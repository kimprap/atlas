# Improvement Plan: Make Atlas cross-harness and CLI-driven without a second public interface

**Datetime**: 2026-08-15-1842
**Authority kind**: direct-repository
**Mode**: deep
**Scope**: Atlas framework contracts, deterministic runtime, agent-facing CLIs, owner resources, and source/topic/research lifecycle
**Summary**: Replace harness-specific transport and duplicated command ceremony with one discoverable façade CLI, one separate instance administration CLI, three cohesive internal owners, purpose-specific topic inspection, and recoverable research publication. Preserve `/atlas-ask` as the only user-facing Atlas interface and canonical Markdown as authority; defer instance-sync durability to a separate project.
**Status**: DONE
**Completed At**: 2026-08-16-2302

## Objective

- Outcome: OUT-ATLAS-CLI
- Observable end state: A fresh agent in any supported harness enters through `/atlas-ask`, selects one owner and mode, discovers the lifecycle operation surface through `scripts/atlas_tool.py`, and completes source, answer, research, refresh, repair, migration, and recovery work without provider-specific framing, agent-authored canonical projections, direct helper-owner chains, or unstructured recovery inference. Internal primitives remain callable and discoverable only through explicit all-operation inspection.
- Progress signal: One of AC-CONTRACTS through AC-INTEGRATED becomes proven, or a named blocker is resolved with the required revision and approval evidence.
- Current evidence: Execution produced the 78-path target `sha256:6c8eb80425a35e71935c175445b16c90faaf66981530f8151e4781d7cdce83d9`; Ruff, the 297-test Atlas suite, 70 fresh focused tests, and temporary CLI smoke passed. The sole review rerun nevertheless found `REV-ATLAS-004` and `REV-ATLAS-005`, leaving AC-CONTRACTS, AC-RESEARCH, and AC-INTEGRATED unmet.
- Intended reduction: Nine internal owner resources become three mode-aware owners; one `OperationSpec` catalog generates command, dispatch, help, and capability surfaces with lifecycle/internal audience metadata; the outer workflow result becomes a compact transport-neutral result with bounded resumability; hosted exact-seven recapture, fresh-assessment machinery, Task-required routing, and automatic engineering-cycle ceremony are removed. The current 41-operation post-cutover arithmetic remains an implementation inventory fact, not an exposed success criterion.
- Current frontier: Terminally blocked under this parent outcome. The run-wide post-assurance repair token and impacted review rerun are consumed; continuation requires a new human-approved parent outcome rather than another repair or lifecycle reset.

- `CONTRACT-CLI-V2` response keys are exactly `version`, `ok`, `op`, `disposition`, `result`, `findings`, and `recovery`. Dispositions are `completed`, `no-write`, `rejected`, `unavailable`, `recovery-required`, `manual-intervention`, and `internal-error`; exits are 0 for the first two, 2 for correctable request/state rejection, 3 for pre-intent availability or I/O failure, 4 for post-intent recovery/manual intervention, and 70 for normalized unexpected framework defects.
- Family command input is one exact operation-args JSON object from `--input -` or one UTF-8 file. Low-level `call` consumes the full version-2 envelope. Nested domain records retain their independent version-1 fields.
- Every immutable `OperationSpec` has `audience: lifecycle|internal`. Default `capabilities` and root/family help advertise lifecycle operations only. `capabilities --all` returns both audiences, including exact command paths, and a known internal command remains directly callable and subject to the same access/capability checks. Audience changes discovery only, never authorization.
- Lifecycle audience is exactly: `url.normalize`, `url.resolve_reference`; `source.inventory`, `source.lookup`, `source.worker_schema`, `source.normalize_capture`, `source.prepare`, `source.snapshot_active`; `quality.validate_proposal`, `quality.validate_summary`; `topic.inspect`; `index.create_topic`, `index.recover_topic`; `research.prepare`, `research.execute`, `research.recover`; `refresh.execute`, `refresh.recover`; `effect.execute`, `effect.recover`; `state.validate`; both versioned migration operations; and `vault.read`, `vault.read_json`, `vault.list`, `vault.hash`, `vault.digest_tree`. Generic vault writes, generic transactions, generic reduction/render/merge helpers, calibration helpers, and `discovery.normalize` are internal.
- `CONTRACT-CAPTURE` input keys are exactly `version`, `requested_url`, `final_url`, `content_type`, `method`, `complete`, `notes`, and `text`; `complete` must be true, content must be nonempty UTF-8 text, and output preserves exact text while deriving byte length and SHA-256. The owner contract, not Python, maps GitHub file-read, OMP native-reader, and generic HTTP/browser results into this schema using a short explicit field table; no generic object-walking fallback is allowed.
- `CONTRACT-TOPIC-INSPECTION` request is exactly `{topic_id,purpose}` with purpose `answer`, `research`, or `refresh`. Common result fields are `version`, `topic_id`, `purpose`, freshness status, typed topic row, typed relation rows, registry revisions, exact artifact revisions used, pending edge IDs in stable order, purpose payload, and `inspection_sha256`; stale or malformed state returns no partial context.
- Inspection hash preimage is canonical JSON of only `topic_id`, `purpose`, sorted registry revision bindings, sorted artifact revision bindings actually used by that purpose, and stable pending edge IDs. Returned Markdown bodies are excluded. A body-only or whitespace-only change with unchanged revisions does not change the hash; any included revision change or pending-edge-set change does. The connector returns revision plus bytes, so a connector that changes bytes under one revision violates CONTRACT-CONNECTOR rather than changing the hash definition.
- Purpose payloads are fixed and bounded. `answer` returns only managed topic sections. `research` returns managed topic sections, the current subdomain index, and source-summary records already related to the topic. `refresh` returns pending-edge records with their referenced source-summary records, managed topic sections, and current pass metadata. No purpose returns every source body or historical pass body.
- `CONTRACT-RESEARCH` prepare request is exactly `{version,topic_id,inspection_sha256,pass_uri,pass_text,index_text,completed_on}`. Eligibility requires a current topic, zero pending edges, and current inspection binding. Target order is pass, topic `INDEX.md`, subdomain `INDEX.md`, then `TOPICS.md`; the first three targets must already be staged with exact preview hashes before the reducer may derive `research-complete` for `TOPICS.md`. Publication cannot create or apply pending edges and cannot add a fifth target. Recovery is exactly `{version,transaction_id,request}` and accepts only the byte-identical original request. Approved outer research mode may reach eligibility through in-process refresh and a new inspection, but `research.prepare|execute` themselves never relax these preconditions.
- Existing `refresh.execute` and `refresh.recover` keep their own journal/state machine and consume a fresh `topic.inspect` binding plus semantic pass/index bytes rather than an agent-authored projection. Refresh preparation is `topic.inspect` plus model drafting; no new `refresh.prepare` catalog operation is added. On approved `research` mode, an initial `dirty|refreshing|blocked` inspection runs this refresh recipe in-process, re-inspects, and proceeds to research preparation only when the new state is current with zero pending edges. Standalone `refresh` stops after refresh; `answer` never refreshes. Existing source/route, effect, index, and migration recovery semantics remain exact and gain structured envelope recovery fields only.
- `CONTRACT-OWNER-RESULT` keys are exactly `version`, `owner`, `outcome`, `effect`, `summary`, `items`, and `next`. `owner` is exactly `atlas-source|atlas-research|atlas-maintain`; `outcome` is exactly `completed|no-write|needs-user|needs-guidance|blocked|framework-defect`; `effect` is exactly `none|committed|partial|unknown`; `items` is outcome-typed, with `needs-user` carrying one batched material question set and `needs-guidance` carrying one bounded missing-semantic set; `next` is null except for exact already-authorized recovery operation/identity. Prepare/preview and every observed no-write path report `effect: none`; `partial` means a journal proves incomplete apply, and `unknown` means post-intent crash or observation disagreement. `partial|unknown` always blocks, cannot pair with `outcome: completed`, and may expose through `next` only the byte-identical already-authorized recovery operation/identity. The result contains no owner dispatch, attempt counters, revisions, engineering-cycle state, or learning candidate.
- Resume ceilings are invocation-local safety guards, not returned or persisted attempt metadata. `atlas-source` may resume at most twice for `needs-user`—first aggregate choice, then worker choice—and once for `needs-guidance`, with an owner-turn ceiling of four. `atlas-research` and `atlas-maintain` may each emit at most one `needs-guidance` result with an owner-turn ceiling of two; unresolved scope or product choice returns to a new front-door invocation rather than widening the approved effect.
- Source inventory tokens remain exactly intent `presence|routine|resummarize` and dispositions `new|active-due|active-not-due|active|archived|duplicate|rejected`; no `explicit-resummarize` disposition is introduced. `source.prepare` continues to return `{event_record,targets}` under its `transaction` member. Owners pass that transaction unchanged to `transaction.execute|recover` and call `transaction.successor` only when the façade reports the sole eligible successor. `effect.execute|recover` remains callable for its existing aggregate-effect envelope and is never inferred as a source-prepare adapter.
- `CONTRACT-RECIPES` covers eight exact paths: Source a URL (`url.normalize` over the explicit URL set -> one `source.inventory` with intent `presence|routine|resummarize`; presence stops read-only, routine processes only `new|active-due`, and resummarize processes only `active` -> `source.lookup` -> external capture -> `source.normalize_capture` -> `source.worker_schema` -> model proposal -> `quality.validate_proposal` and `quality.validate_summary` -> `source.prepare` -> `transaction.execute|recover` -> `transaction.successor` only when the façade reports the sole eligible successor -> source-owner in-process route); Answer a topic (`topic.inspect` purpose `answer`, no write or refresh); Research a topic (`topic.inspect` purpose `research` -> when `dirty|refreshing|blocked`, run the Refresh recipe in-process and re-inspect -> require current state and zero pending edges -> model draft -> `research.prepare` -> `research.execute|recover`); Refresh a dirty topic (`topic.inspect` purpose `refresh` -> model draft -> re-inspect -> `refresh.execute|recover`, then stop for standalone refresh mode); Create a topic (`topic.inspect` proves absent -> `index.create_topic|recover_topic`); Explicit reroute (`source.lookup` -> route's fresh `source.lookup` of the same canonical URL -> `vault.read` of the bound artifact and registries -> `state.validate` -> existing bounded route decision -> `state.reduce` route-upsert -> `source.render_route_artifact` -> `transaction.execute|recover` -> `transaction.successor` only when the façade reports an eligible successor; zero `source.snapshot_active`, inventory, capture, `source.prepare`, or source hash/date refresh); Repair/migrate (`vault.read|read_json|list|hash|digest_tree` plus `state.validate` -> `migration.prepare_topics_lists` -> separately approved `migration.apply_topics_lists` -> exact returned recovery path); and Preview vs commit (prepare/preview operations report `effect: none`; execute/apply operations own writes; `partial|unknown` blocks and reuses the returned recovery identity byte-for-byte). `effect.execute|recover` remains a lifecycle catalog pair but is not the post-`source.prepare` or post-route-render adapter. The asset names only operation literals present in `OperationSpec`; a lifecycle-command index lists each lifecycle family command exactly once, with no stale shell, direct owner, or `vault.conditional_replace` path.
